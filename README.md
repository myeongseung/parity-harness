# parity-harness

[![CI](https://github.com/myeongseung/parity-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/myeongseung/parity-harness/actions/workflows/ci.yml)

**레거시를 정답(golden)으로 삼아, 이관 결과가 원본과 같은지를 기계적으로 증명하는 마이그레이션 하네스.**

> **상태: 완결 (2026-08-21).** 1단계(89화면 1:1 정합)와 2단계(결함 수정 16건,
> D-100~D-115)가 끝났다. 검증 4종 초록 — 게이트 PASS · 스타일시트 88/88 ·
> 실화면 글자 PASS · 실화면 그림 다름 0. 디자인 변경과 기능 업그레이드는 이
> 소스를 가져가 **새 저장소에서** 진행한다. 넘어가는 목록은
> [결정 로그의 종결 절](migration/design/00-decisions.md)에 있다.

시중의 AI 마이그레이션 도구는 대부분 *변환*에서 멈춘다. 변환 결과가 맞는지는 사람이 눈으로 본다.
이 프로젝트의 전제는 반대다 — **변환은 쉽고, 정합성 증명이 어렵다.**

**두 방향을 모두 본다** — 없던 것이 생겼는가(`check_no_invention`), 있던 것이
사라졌는가(`check_completeness`). 누락이 더 조용하다. 없던 버튼이 생기면 눈에 띄지만
있던 버튼이 사라지면 화면은 멀쩡해 보인다.

```
parity-harness/   정합성 게이트 (도메인 중립)
legacy/           이관 대상 원본 = 정답 (ERFlow, MIT / jUqItEr)
migration/        실제 이관 — 하네스가 실전에서 통하는지의 증거
```

> 코드를 읽기 전에 맥락이 필요하다면 — [**변환은 쉽고, 증명이 어렵다**](docs/%EB%B3%80%ED%99%98%EC%9D%80-%EC%89%BD%EA%B3%A0-%EC%A6%9D%EB%AA%85%EC%9D%B4-%EC%96%B4%EB%A0%B5%EB%8B%A4.md)
> 왜 만들었고, 무엇을 잘못했고, **이 방법으로 못 잡는 것은 무엇인지**를 글로 정리했다.

## 무엇을 막는가

LLM 기반 마이그레이션의 최대 실패 모드는 버그가 아니라 **친절함**이다.

레거시에 없던 엑셀 다운로드 버튼을 추가하고, 없던 안내 문구를 넣고, 콤보박스에 없던 항목을
하나 더 만든다. 전부 그럴듯해서 **코드 리뷰에서 걸리지 않는다.** 컴파일러도 테스트도 못 잡는다.
문법적으로 옳고 동작도 하기 때문이다.

잡으려면 **레거시에 무엇이 있었는지를 정답으로 고정**해야 한다.

```
$ python -m gates.check_no_invention --golden golden/unitList.json --new templates/unit/list.html

차이 3건  (HIGH 1 / MEDIUM 2)  [invention 1 / detail_change 2]

  HIGH   list.html:31
         control:button «엑셀 다운로드» [button]
         레거시에 대응물 없음 — 없던 것을 만들어냈다
         조치: 요소를 제거하거나, 의도적이면 allowlist 에 사유와 함께 등록
```

## 설계에서 중요한 것

**모를 때 통과시키지 않는다.**

```
0  PASS      정합성 확인됨
1  FAIL      위반 발견 (자동 보강 가능)
2  ERROR     도구/설정 오류
3  ESCALATE  정답 부재 또는 추출기 버전 불일치 -> 사람 판단
```

3을 1과 분리한 것이 핵심이다. 정답이 없으면 "위반 없음"이 아니라 "판정 불가"다.
추출 규칙을 바꾸고 정답을 다시 뽑지 않아도 여기 걸린다 — **낡은 기준으로 통과시키는 것이
가장 나쁜 실패**이기 때문이다.

**차이를 세 갈래로 나눈다.** 조치가 완전히 다르기 때문이다.

| 분류 | 조건 | 조치 |
|---|---|---|
| `invention` | 대응물이 없다 | 제거하거나 사유와 함께 예외 등록 |
| `label_drift` | 닮은 라벨이 있다 | 레거시 원문 표기로 복원 |
| `detail_change` | 라벨이 같고 대상만 다르다 | 라우트 변경이면 의도된 것. **라벨은 건드리지 않는다** |

셋을 뭉뚱그리면 리포트가 엉뚱한 조치를 지시한다. 라우트를 새로 설계하는 이관에서는 모든
링크가 `detail_change` 에 걸리는데, 이것을 "표기가 틀어졌다"고 보고하면 사람이 멀쩡한
라벨을 고치게 된다.

**예외는 허용하되 기록을 남긴다.** 사유 10자 미만이면 게이트 자체가 실패한다.

## 실전 검증: ERFlow

JSP + Servlet(Model 1) ERP 를 Spring Boot 4 / MyBatis / MariaDB 로 이관하며 하네스를 검증했다.
레거시가 **동작하는 DB 로 살아 있어** 실제 데이터로 대조할 수 있다.

| 레거시 | |
|---|---|
| JSP | 145개 |
| Java | 134개 / 16,844 LOC |
| 테이블 | 32개 + 뷰 15개 (2,077행) |
| 아키텍처 | Model 1. 라우팅 없음, raw JDBC, 화면에 권한 검사 39곳 |

| 진행 | 상태 |
|---|---|
| 스키마 복제 | 32테이블·15뷰, 행수·한글 정렬 결과 일치 |
| 레이아웃 | 메뉴를 테이블로 분리. 검증량 **145회 → 2회** |
| 인증·권한 | Spring Security. 레거시 해시 1:1 재현, 화면별 권한 한 곳에서 판정 |
| 화면 | **89화면 전부 이관. 게이트 PASS** |
| 실화면 대조 | 레거시를 띄워 글자·픽셀 대조 — 그림 같음 57 / 다름 0 / 순서 무관 3 |
| 2단계 결함 수정 | 레거시 결함 16건 해소·종결 (D-100~D-115) |

테스트: 하네스 72건 / 앱 348건.

### 하네스가 실제로 값을 하는가

`unit` 은 하네스를 만들어 가며, `company` 는 완성된 하네스로 이관했다. 두 도메인은
화면 구성이 같아 비교가 공정하다.

| | `unit` | `company` |
|---|---|---|
| **범용 게이트 수정** | 11회 | **2회** |
| 정답 추출 성공까지 | 6회 수정 | **0회** |
| 최종 게이트 | PASS · 차이 0 | PASS · 차이 1 (라우트 변경) |

성격도 다르다. `unit` 에서 고친 것은 대부분 **판정 자체의 오류**였고
(`value` 를 라벨로 읽는 등), `company` 에서 고친 둘은 **처음 만난 문법**이었다.

### 하네스는 실제 코드에 붙여야 완성된다

가상 예제로는 통과하던 게 실제 JSP 에서 11번 깨졌다. 전부 회귀 테스트로 고정돼 있다.

| | 증상 | 원인 |
|---|---|---|
| 1 | 자바 코드가 화면 텍스트로 | HTML 파서에게 `<%` 는 태그가 아니다 |
| 2 | 라벨이 «>전체조회» | `%>` 의 `>` 가 태그를 조기 종료 |
| 3 | 삭제 버튼 라벨이 «delete» | `value` 는 데이터지 라벨이 아니다 |
| 4 | 수정 버튼이 «dyn» | 3번을 고치다 만든 과교정 |
| 9 | 자식의 시안용 더미가 부모 링크 라벨로 | `deep_text` 가 자식의 `th:text` 를 모름 |
| 11 | 낡은 정답으로 판정 | 추출기 버전 기록으로 ESCALATE |

### 레거시를 띄워 실화면끼리 견준다

레거시가 **동작하는 앱으로** 살아 있다. 소스는 손대지 않고, 빌드할 때 DB 접속
자리표시자만 채워 WAR 로 묶는다(`migration/legacy-runtime/`). 두 앱을 같은 스키마에
붙이고 같은 계정으로 로그인해 같은 화면을 받아 견준다.

```
$ python migration/tools/compare_live.py

PASS  생산 설비 관리: 15행 일치
PASS  협력업체 관리 (구매): 양쪽 다 권한으로 막힘
PASS  게시글 목록 (자유게시판): 13행 일치
PASS  게시글 보기: 3건 일치

== 조회수 집계 규칙 ==
PASS  처음 보는 글 (쿠키에 없음): 양쪽 다 +0
KNOWN 이미 본 글 (쿠키에 있음): 레거시 500 (쿠키 값의 ';' — D-033), 신규는 정상
```

**권한으로 막힌 것도 결과로 본다.** 오류로 처리하면 "둘 다 막혔다"를 확인할 수 없는데,
레거시에서 막히던 사람이 신규에서 통과하면 그것이야말로 이관 사고다.

**이 단계에서 바로 하나 나왔다.** 게이트는 6화면 전부 PASS 였는데 날짜 형식이 달랐다.

```
레거시   2023년 06월 20일
신규     2023-06-20
```

날짜는 서버가 채우는 자리라 signature 가 `«dyn»` 이다. 값을 모르는 것끼리 견주므로
**형식이 달라도 게이트는 통과한다** — 원리상 못 잡는 자리다. 같은 이유로 CSS 가
걸렸는지, JS 가 죽었는지도 못 본다.

### 한 번 받아 보는 것으로는 부족하다

게시판을 이관하며 더 깊은 것이 나왔다. **레거시는 이미 본 글을 다시 열면 죽는다.**

```
java.lang.IllegalArgumentException: 쿠키 값에 유효하지 않은 문자 [59](;)가 있습니다.
        at org.apache.jsp.post.postView_jsp._jspService(postView_jsp.java:227)
```

조회수 중복 집계를 막으려고 본 글 번호를 세미콜론으로 이어 붙이는데, 그 글자는 쿠키
값에 들어갈 수 없다. 게다가 그 판정 조건이 뒤집혀 있어서(`D-029`) 실제 동작은 이렇다.

| 순서 | 동작 |
|---|---|
| 아무 글이나 처음 열기 | 조회수 +1 |
| 다른 글 열기 | **조회수 안 오름** |
| 처음 열었던 글 다시 열기 | **500** |

브라우저 하나당 한 시간에 글 하나만 조회수가 오르고, 그 글은 다시 열 수 없다.

**어디까지 안 보였는지가 요점이다.**

| 검사 | 결과 |
|---|---|
| 정합성 게이트 | 통과. 조회수는 `«dyn»` 이고 쿠키는 마크업에 없다 |
| 화면 한 번 받아 대조 | 통과. **첫 조회는 정상이다** |
| 규칙을 여러 번 돌린 대조 | 여기서 잡혔다 |

상태를 바꾸는 화면은 한 번 받아 보는 것으로 부족하다. 그래서 화면을 두 번씩 열어
증가분을 양쪽에서 견주는 검사를 넣었다.

### 대조가 대상을 바꾼다

같은 화면에서 함정을 하나 더 만났다. 두 앱이 같은 스키마를 보므로 게시글 보기를
그냥 열면 **먼저 연 쪽이 조회수를 올려 놓아** 뒤에 연 쪽과 값이 달라진다. 처음에
그것을 결함으로 보고했다가 원인을 찾았다.

막은 방법이 마음에 든다 — `D-029` 의 뒤집힌 조건을 역이용했다. 어떤 글 번호와도
겹치지 않는 쿠키를 심으면 양쪽 다 조회수를 올리지 않는다. **결함이 시험 도구가 됐다.**

### 게이트가 못 잡는 것

하네스에는 구조적 한계가 있고, 실제로 걸렸다.

`company` 를 시작하며 앞서 기록한 결정 하나를 **철회**했다. "영업 화면이 구매 권한으로
제어된다"고 적었는데 틀렸고, 원인은 정답 생성기가 화면 파일에서 **첫 권한 코드만 읽은
것**이었다. 같은 실수로 10개 화면이 잘못 매핑돼 있었다.

**게이트는 "정답 대비 다른가"를 보지 "정답이 맞는가"는 보지 않는다.** 정답 추출이
원본의 일부만 보고 있으면 조용히 통과한다. 발견한 것은 게이트가 아니라 사람이 원본을
읽은 일이었다.

고친 방향은 **모르면 멈추게** 하는 것이다 — 권한 코드가 둘 이상인 화면에 판별 규칙이
없으면 생성기가 그 자리에서 중단한다.

**같은 일이 세 번 더 있었다.** 게시판을 시작하며 원본을 읽다가, 추출기가 아예 보지
않던 요소들이 드러났다.

| 놓치던 것 | 규모 |
|---|---|
| `<i title="검색하기">` 툴팁 | 89화면 중 **22화면** — 이미 이관한 두 화면 포함 |
| `<img alt="첨부파일">` | 첨부 여부를 알리는 유일한 표시 |
| `href` 없는 `<a>` | 댓글의 "수정하기"·"답글달기" |

세 번 다 **사람이 원본을 읽다가** 찾았다. 게이트가 스스로 알려준 적은 없다.

반대 방향도 하나 있었다. `<a href="#comment"></a>` 처럼 라벨도 대상도 없는 앵커가
정답에 남아 있어서, **신규 구현에 빈 앵커를 만들라고 강요하고 있었다.** 정답이
발명을 요구한 셈이다.

**아는 사각지대는 닫는다.** `readonly` 입력의 `value` 는 사용자가 고칠 수 없으니
화면에 박힌 글자다. 이것을 안 봐서 레거시 글쓰기 화면의 하드코딩된 게시판 이름을
놓쳤다(D-032). 규칙을 고치고 **실제로 닫혔는지 확인했다** — 하드코딩을 동적으로
"고쳐" 보면 양쪽 게이트가 HIGH 로 막는다(D-034).

닫지 못하는 것은 그대로 두되 이유를 적었다. 날짜 형식은 자바 코드에 있고, 스크립틀릿
출력은 자바를 해석해야 하고, 조회수 규칙은 마크업에 없다. **할 수 있는데 안 하는
것과 원리상 못 하는 것은 다르다.**

### 덤으로 찾은 레거시 결함

정답을 추출하다 드러난 것들. **고치지 않고 그대로 재현**했다 — 이관 중에 동작을 바꾸면
"레거시와 같은가"를 검증할 수 없게 된다. 전부 결정 로그에 기록돼 있다.

- **업체 종목 검색이 아무것도 못 찾으면 500 에러가 난다.** `"".substring(1)` — 빈 `IN ()` 을 만들다 죽는다
- **권한 없이도 등록 요청이 통했다.** 화면은 권한을 검사하는데 처리 페이지는 로그인만 봤다
- `program_id = SHA256(한글 프로그램명)` — 권한 테이블의 오타("결재관리 관리")를 고치면 권한이 통째로 깨진다
- `aria-label=".form-select-sm example"` — Bootstrap 문서 예제 문구가 복사됨
- 라벨도 `name` 도 `id` 도 없는 입력 — 화면에 보이기만 하고 서버로 가지 않는다
- 사용자 55명 중 42명이 비밀번호 = 사번

cd parity-harness
python -m unittest discover -s tests -t .        # 의존성 없음. 표준 라이브러리만

# 정답 추출 -> 게이트
python -m gates.extract_golden --legacy ../legacy/ERFlow/src/main/webapp/unit/unitList.jsp \
    --screen unit-list -o /tmp/golden.json

## CI 가 무엇을 보는가

푸시마다 세 가지를 돌린다.

| | |
|---|---|
| 하네스 테스트 | 72건 |
| 정합성 게이트 | 비밀 잔존 · 정답 재생산 · 메뉴 · 발명 차단 · 누락 차단 (`run_gates.py`) |
| 앱 빌드 | 컴파일 + Checkstyle + 테스트 |

**정답 재생산 검사**가 이 CI 의 핵심이다. 레거시에서 정답을 다시 뽑아 저장소의 것과
견준다 — 추출 규칙을 고치고 정답을 갱신하지 않았거나 정답을 손으로 고쳤다면 여기서
걸린다. 그런 정답으로 내린 판정은 믿을 수 없기 때문이다.

**한계도 적어 둔다.** 앱 테스트 348건 중 CI 에서 실제로 도는 것은 **75건**이다. 나머지
273건은 연결된 DB 를 상대로 하므로 접속 정보가 없는 CI 에서는 스스로 건너뛴다
(접속 정보는 커밋하지 않는다). 배지가 초록이어도 DB 대조는 로컬에서 돌려야 한다.
