# 변환은 쉽고, 증명이 어렵다

## — 레거시 마이그레이션에서 "정말 같은가"를 기계로 확인한 기록

JSP + Servlet으로 된 20년쯤 묵은 스타일의 ERP를 Spring Boot로 옮기는 일을 했다.
화면 145개, 자바 134개, 테이블 47개.

요즘은 이런 걸 LLM에게 시킬 수 있다. 실제로 화면 하나를 옮기는 데 몇 분이면 된다.
**그런데 옮긴 게 원래랑 같은지는 누가 확인하나?**

이 글은 그 질문에 기계로 답해보려 한 기록이다. 결론부터 말하면 — 답을 얻긴 했는데,
**답을 얻는 과정보다 "이 방법으로는 못 잡는 것"을 알아내는 쪽이 훨씬 어려웠다.**

---

## 1. LLM 마이그레이션의 실패 모드는 버그가 아니다

처음엔 이렇게 생각했다. *"컴파일되고 테스트 통과하면 되는 거 아닌가?"*

아니었다. 진짜 문제는 이거다.

```
레거시 화면:  [삭제] [추가]  |  검색 ▾
신규 화면:    [삭제] [추가] [엑셀 다운로드]  |  검색 ▾  [초기화]
```

없던 엑셀 다운로드 버튼이 생기고, 없던 초기화 버튼이 붙는다. 없던 안내 문구가
들어가고, 콤보박스에 없던 항목이 하나 더 생긴다.

**전부 그럴듯하다.** 문법적으로 옳고, 동작하고, 오히려 더 좋아 보인다. 그래서
컴파일러도 테스트도 코드 리뷰도 못 잡는다. 리뷰어는 "오, 엑셀 다운로드 좋네요"
하고 넘어간다.

LLM 마이그레이션의 최대 실패 모드는 **버그가 아니라 친절함**이다.

그리고 이건 운영에서 이렇게 돌아온다 — *"이 버튼 뭐죠? 우리 이런 거 없었는데."*

---

## 2. 그래서 정답을 고정했다

잡으려면 **레거시에 무엇이 있었는지**를 기계가 읽을 수 있는 형태로 박아둬야 한다.

레거시 화면에서 "의미 있는 요소"만 뽑아 정규화한다.

```
kind : role | label | detail

control:button|삭제|button
column:header|장비명|
option:item|전체조회|
nav:link|생산 설비 관리|/unit/list
```

핵심은 **모든 요소를 비교하지 않는 것**이다. DOM 전체를 diff하면 레이아웃 wrapper
차이만으로 노이즈가 폭발한다. 사용자가 인지하거나 상호작용하는 것만 본다.

그리고 이 표현은 **스택 중립적**이어야 한다.

| 레거시 (JSP) | 신규 (Thymeleaf) | signature |
|---|---|---|
| `<input type="submit" value="조회">` | `<button type="submit">조회</button>` | `control:button\|조회\|submit` |

태그도 클래스도 다르지만 같은 요소로 인식된다. 이 정규화 계층이 전부다.

---

## 3. 설계에서 제일 중요했던 두 가지

### 모를 때 통과시키지 않는다

```
0  PASS      정합성 확인됨
1  FAIL      위반 발견
2  ERROR     도구 오류
3  ESCALATE  정답 부재 -> 사람 판단
```

**3을 1과 분리한 게 핵심이다.** 정답 파일이 없으면 "위반 없음"이 아니라 "판정 불가"다.
이걸 0으로 처리하면 정답을 안 만든 화면이 전부 조용히 통과한다.

나중에 여기에 하나 더 붙였다 — **추출 규칙을 바꾸고 정답을 다시 안 뽑았을 때**도
ESCALATE. 낡은 기준으로 판정하는 게 "정답이 틀렸는데 통과"라 가장 나쁜 실패다.

### 차이를 세 갈래로 나눈다

처음엔 "다르면 다르다"로 뭉뚱그렸다. 그러니 리포트가 **엉뚱한 조치를 지시**했다.

| 분류 | 조건 | 조치 |
|---|---|---|
| 발명 | 대응물이 없다 | 제거하거나 사유와 함께 예외 등록 |
| 라벨 드리프트 | 닮은 라벨이 있다 | 원문 표기로 되돌린다 |
| 대상 변경 | 라벨이 같고 링크만 다르다 | **라벨은 건드리지 않는다** |

이관에서 라우트를 새로 설계하면 모든 메뉴 링크가 세 번째에 걸린다. 이걸
"표기가 틀어졌다"고 보고하면 **사람이 멀쩡한 라벨을 고친다.** 실제로 그럴 뻔했다.

## 4. 하네스는 실제 코드에 붙여야 완성된다

가상 예제로 만든 게이트를 진짜 JSP에 붙였더니 **11번 깨졌다.**

가장 인상적이었던 건 이거다.

```html
<button type="button" name="flag" value="delete">삭제</button>
```

게이트가 이 버튼의 라벨을 **`delete`** 로 읽었다. `value`를 먼저 봤기 때문이다.

사용자가 보는 건 "삭제"고 `value`는 서버로 보내는 코드값이다. 같은 함정이 세 군데에
있었다.

```html
<option value="10">경영지원</option>          <!-- 부서 코드가 바뀌면 오탐 -->
<input name="unitName" value="<%=name%>">     <!-- 수정 폼이 전부 «dyn» -->
```

**`value`는 데이터지 라벨이 아니다.** 버튼류 input만 예외다(안쪽 텍스트가 없으니까).

또 하나. `<%` 를 HTML 파서에게 주면 태그가 아니라 텍스트다. 그래서 자바 코드가
화면 문구로 잡히고, `%>` 의 `>` 가 태그를 조기 종료시켜 라벨이 `>전체조회` 가 됐다.

그리고 **자기가 만든 오탐**도 있었다. 위 문제를 고치면서 "속성에 표현식이 있으면
동적"으로 처리했더니, `data-id="<%=id%>"` 때문에 **"수정" 버튼 라벨이 사라졌다.**
라벨의 출처가 될 수 있는 속성으로 범위를 좁혀 다시 고쳤다.

교훈은 단순하다 — **정합성 도구는 가상 예제로 검증되지 않는다.**

## 5. 그런데, 게이트가 못 잡는 것이 있었다

여기부터가 진짜다.

### 5-1. 정답 자체가 틀렸을 때

두 번째 도메인을 시작하며 원본을 읽다가 이걸 봤다.

```java
final String IN_PROGRAM_CODE  = "4F6B2188...";   // 구매
final String OUT_PROGRAM_CODE = "90739BBD...";   // 영업
switch (paramFlag) { case "0": ... case "1": ... }
```

한 화면이 파라미터에 따라 **다른 권한**을 요구하고 있었다. 그런데 내 정답 생성기는
**파일에서 첫 번째 코드만 읽고 있었다.** 같은 실수로 10개 화면이 잘못 매핑돼 있었다.

앞서 나는 이걸 "레거시의 권한 결함"이라고 기록해뒀었다. 결함이 아니라 **내 도구의
버그**였다. 기록을 철회했다.

**게이트는 이걸 못 잡는다.** 게이트는 "정답 대비 다른가"를 볼 뿐 "정답이 맞는가"는
보지 않는다. 정답 추출이 원본의 일부만 보고 있으면 조용히 전부 통과한다.

발견한 건 게이트가 아니라 **사람이 원본을 읽은 일**이었다.

고친 방향은 **모르면 멈추게** 하는 것이다. 권한 코드가 둘 이상인 화면에 판별 규칙이
없으면 생성기가 그 자리에서 중단한다. 아무거나 고르면 절반이 엉뚱한 권한을 갖고,
그 사실이 드러나지 않는다.

**같은 일이 세 번 더 있었다.** 세 번째 도메인을 시작하며 원본을 읽다가, 추출기가
*아예 보지 않던* 요소들이 드러났다.

| 놓치던 것 | 규모 |
|---|---|
| `<i title="검색하기">` 툴팁 | 89화면 중 **22화면** — 이미 이관을 끝낸 두 화면 포함 |
| `<img alt="첨부파일">` | 게시글에 첨부가 있는지 알리는 유일한 표시 |
| `href` 없는 `<a>` | 댓글의 "수정하기"·"답글달기" |

첫 번째가 뼈아프다. 이미 이관한 화면에도 있었는데, 확인해보니 내 템플릿에는 살아
있었다 — **마크업을 그대로 옮겨서지 게이트가 요구해서가 아니었다.** 지웠어도 통과했다.

반대 방향도 하나 있었다. `<a href="#comment"></a>` 처럼 라벨도 대상도 없는 앵커가
정답에 남아 있어서, 신규 구현에 **빈 앵커를 만들라고 강요**하고 있었다. 정답이
발명을 요구한 셈이다.

### 5-2. 값이 동적인 자리

게이트가 6화면 전부 PASS였다. 그래서 레거시를 실제로 띄워 나란히 놓았다.

```
레거시   2023년 06월 20일
신규     2023-06-20
```

날짜 형식이 달랐다.

**이건 원리상 못 잡는다.** 날짜는 서버가 채우는 자리라 signature가 `«dyn»`이다. 값을
모르는 것끼리 견주므로 형식이 달라도 통과한다. 같은 이유로 CSS가 걸렸는지, JS가
죽었는지도 못 본다.

그래서 레거시를 WAR로 묶어 띄우고 두 앱의 화면을 실제로 받아 비교하는 단계를 뒀다.
소스는 손대지 않고 빌드할 때 DB 접속 자리표시자만 채웠다.

```
PASS  생산 설비 관리: 15행 일치
PASS  협력업체 관리 (구매): 15행 일치
PASS  협력업체 관리 (영업): 15행 일치
```

### 5-3. 한 번 받아 보는 것으로 부족할 때

여기까지가 두 번째 도메인의 이야기다. 세 번째 도메인(게시판)에서 **더 깊은 것**이
나왔다.

게시글 보기 화면을 나란히 열었더니 조회수가 `7` 과 `8` 로 달랐다. 결함인 줄 알고
파고들었는데 아니었다. **두 앱이 같은 DB 를 보므로, 먼저 연 쪽이 조회수를 올려
놓고 나중에 연 쪽이 그 값을 읽은 것**이었다.

*측정이 대상을 바꾸고 있었다.*

막으려고 레거시의 조회수 규칙을 읽다가 이것을 봤다.

```jsp
if (cookie == null) {
    updateCount(postId);                              // 쿠키가 없으면 올린다
} else {
    if (cookiePostList.indexOf(postId + "") != -1) {  // 목록에 있으면
        cookie.setValue(cookie.getValue() + ";" + postId);
        updateCount(postId);                          // 또 올린다
    }
}
```

중복 집계를 막으려던 조건이 **뒤집혀 있다.** 처음 보는 글은 세지 않고, 이미 본 글만
볼 때마다 센다.

그리고 그 상태로 실제로 돌려 봤더니 500 이 났다.

```
java.lang.IllegalArgumentException: 쿠키 값에 유효하지 않은 문자 [59](;)가 있습니다.
        at org.apache.jsp.post.postView_jsp._jspService(postView_jsp.java:227)
```

세미콜론은 쿠키 값에 들어갈 수 없다. **이미 본 글을 다시 열면 페이지가 죽는다.**
둘을 합치면 실제 동작은 이렇다.

| 순서 | 동작 |
|---|---|
| 아무 글이나 처음 열기 | 조회수 +1 |
| 다른 글 열기 | 조회수 안 오름 |
| 처음 열었던 글 다시 열기 | **500** |

브라우저 하나당 한 시간에 글 하나만 조회수가 오르고, 그 글은 다시 열 수 없다.
20년쯤 그렇게 돌았을 것이다.

**어디까지 안 보였는지가 요점이다.**

| 검사 | 결과 |
|---|---|
| 정합성 게이트 | 통과. 조회수는 `«dyn»` 이고 쿠키는 마크업에 없다 |
| 화면 한 번 받아 대조 | 통과. **첫 조회는 정상이다** |
| 규칙을 여러 번 돌린 대조 | 여기서 잡혔다 |

상태를 바꾸는 화면은 **한 번 받아 보는 것으로 부족하다.** 화면을 두 번씩 열어
증가분을 양쪽에서 견주는 검사를 넣었다.

측정 오염을 막은 방법이 마음에 든다 — 저 뒤집힌 조건을 역이용했다. 어떤 글 번호와도
겹치지 않는 쿠키를 심으면 양쪽 다 조회수를 올리지 않는다. **결함이 시험 도구가 됐다.**

## 6. 그래서 하네스가 값을 했는가

처음 두 도메인은 화면 구성이 같아서(목록·등록·수정) 비교가 공정하다.

| | 첫 번째 (만들며 이관) | 두 번째 (완성 후 이관) |
|---|---|---|
| 게이트 수정 | **11회** | **2회** |
| 정답 추출 성공까지 | 6회 수정 | **0회** |

숫자보다 **성격의 차이**가 중요하다.

첫 번째에서 고친 것은 대부분 **판정 자체의 오류**였다(`value`를 라벨로 읽는 등).
하나를 고치면 다른 화면도 같이 옳아진다.

두 번째에서 고친 둘은 **처음 만난 문법**이었다. 판정 논리는 건드리지 않았다.

### 그런데 세 번째에서 다시 깨졌다

모양이 다른 도메인(게시판 — 계층 답글, 댓글, 첨부)을 붙이자 **판정 자체의 오류가
네 번 더 나왔다.** 앞의 세 개는 위에 적은 "보지 않던 요소들"이고, 하나 더 있었다 —
`th:text` 가 붙으면 textarea 의 placeholder 라벨까지 «dyn» 으로 봤다.

그러니 "두 번째에서 2회로 줄었다"는 숫자를 **하네스가 완성됐다는 뜻으로 읽으면
안 된다.** 같은 모양을 한 번 더 한 것뿐이었다. 새로운 모양이 오면 또 깨진다.

정직하게 말하면 이렇다 — **하네스는 자기가 본 적 있는 종류의 화면에서만 신뢰할 수
있다.** 그래서 화면 목록에 "아직 이관 안 함" 표시를 두고 리포트에 계속 띄운다.
조용히 건너뛰는 것과 드러내 놓고 미루는 것은 다르다.

## 7. 마지막에 발견한 것

공개 저장소로 돌리기 전에 이력을 훑었다.

```java
new PasswordAuthentication("...", "crvr **** **** ****")   // Gmail 앱 비밀번호
```

레거시 소스에 **살아있는 자격증명**이 평문으로 박혀 있었다. DB 덤프에는 사용자
55명분의 개인정보 형식 데이터도 있었다(확인해보니 주민번호 검증숫자가 51개 중
5개만 맞는 생성 데이터였지만, 읽는 사람은 그걸 알 수 없다).

여기서 원칙이 부딪혔다. 이 프로젝트는 **"레거시는 정답이니 수정하지 않는다"** 를
지켜왔다. 하지만 그 원칙이 살아있는 자격증명을 공개하는 근거가 될 수는 없다.
예외로 두고, 범위와 근거를 기록했다.

그리고 — 마스킹 스크립트를 만들어 이력을 재작성한 뒤 다시 검사했는데,
**여전히 걸렸다.**

```python
REPLACEMENTS = (("<여기에 진짜 비밀번호가 그대로>", "[REDACTED]"), ...)
```

**가리려는 문자열을 마스킹 스크립트에 적어뒀다.** 스크립트가 그걸 공개하고 있었다.
대상 목록을 별도 파일로 분리하고(커밋 제외) 다시 재작성했다.

그리고 이 글을 쓰면서 **또 같은 실수를 했다.** 위 코드 블록에 처음엔 진짜 비밀번호를
그대로 적어놨다. 하필 "원문을 적으면 유출된다"를 설명하는 문단에서. 검사 스크립트를
돌려서야 알았다.

이 실수가 이 글에서 제일 마음에 든다. **검증 도구를 만들면서도 검증 도구 자신을
검증하지 않았다.** 정확히 5-1에서 배운 것과 같은 종류의 실수였는데도, 세 번을 반복한
뒤에야 "검사를 자동으로 돌린다"는 결론에 도달했다.

교훈이 있다면 — 사람의 주의력에 기대는 규칙은 지켜지지 않는다. **기계가 확인하게
만들어야 한다.** 이 프로젝트가 처음부터 하려던 말이 정확히 그것이었는데도.

## 정리

- **변환은 쉽고 증명이 어렵다.** LLM은 화면을 몇 분에 옮기지만, 같은지는 답하지 않는다
- **실패 모드는 버그가 아니라 친절함**이다. 없던 걸 그럴듯하게 추가한다
- **모를 때 통과시키지 않는 게** 게이트 설계의 전부다
- **정합성 도구는 가상 예제로 검증되지 않는다.** 실제 코드에 붙여야 완성되고,
  **새로운 모양이 오면 또 깨진다**
- **상태를 바꾸는 화면은 한 번 받아 보는 것으로 부족하다.** 규칙을 여러 번 돌려야
  드러난다. 그리고 두 앱이 같은 DB 를 보면 **측정이 대상을 바꾼다**
- 그리고 무엇보다 — **게이트는 "정답이 맞는가"를 보지 않는다.** 그건 사람이 원본을
  읽어야 알 수 있고, 도구는 모를 때 멈추는 것까지가 할 수 있는 일이다
